Bonus features evidence - Assignment 4
========================================

All eight applicable §11 bonus items, with real, live-captured evidence (no
simulated output). This folder supplements 01-05, which cover the core
(non-bonus) assignment requirements. Built and evidenced in two passes -
items 1-5 first, items 6-8 afterward - now combined into one folder since
they're the same category of deliverable, just added in separate sessions.
Everything reflects the final, fully-fixed pipeline; every file was
re-captured against real builds after an earlier pass (documented below and
in the commit history) turned up real bugs that made the first round of
evidence unrepresentative of what the pipeline actually does today.

3. Cosign signing (AWS KMS)
   04-cosign-sign-console-output.txt
     - Real `cosign sign --key awskms://... --use-signing-config=false
       --tlog-upload=false` console output for all three services, from
       build #10 - the actual pipeline run, not a manual reproduction.
       Registry auth tokens redacted (same reasoning as above).
   05-cosign-verify-proof.txt
     - Two real `cosign verify` runs, both against the frontend image
       build #10 actually signed (not re-signed, not substituted):
       attempt 1 (default flags) fails with "not enough verified log
       entries from transparency log: 0 < 1" - expected, not a bug: this
       signature genuinely has no Rekor entry, because --tlog-upload=false
       deliberately disabled that upload (see README §5's Signing
       paragraph for why). Attempt 2, with --insecure-ignore-tlog=true,
       succeeds cleanly: "The signatures were verified against the
       specified public key" is a genuine cryptographic check against the
       real KMS key, not a log message. An earlier pass at this evidence
       showed a misleading "clean" success with no flags at all - that
       image had been re-signed on top of an earlier, not-yet-fixed
       signature that still had a real Rekor entry, so verify was quietly
       finding *that* one. Redone here against a digest signed exactly
       once, with the final flags, to remove that ambiguity.

4. Automated rollback
   06-rollback-scenario1-first-deploy-no-prior-revision.txt
     - cd-application build #1 (this app's actual first-ever deploy).
       Deploy/Rollout/Verify succeeded; Smoke Test failed (cold ELB DNS
       propagation, unrelated to rollback); automated rollback triggered.
     - Shows the ORIGINAL bug, not the fix: at the time this build ran, the
       Jenkinsfile didn't yet guard against "no prior revision to roll
       back to" - `helm rollback` errored with "release has no 0 version"
       and crashed the whole post{failure{}} block. This is exactly the
       real failure that led to the fix in commit 98bdf4c (jenkins/cd/
       Jenkinsfile's REVISION_LINES check) - kept as evidence of a real
       bug found by an actual first deploy, not invented for the write-up.
   07-rollback-scenario2-real-rollback-executed.txt
     - cd-application build #2, run with the fix in place. Same failure
       shape (Smoke Test failed after a real revision was live), but this
       time a prior revision existed: `helm history` reported 3 lines (2
       revisions), the guard correctly proceeded, and `helm rollback`
       executed for real - "Rollback was a success! Happy Helming!" -
       reverting devops-app to the previous, working revision.

9. JCasC-first recovery
   15-jcasc-recovery-drill-proof.txt
     - Full destroy-and-rebuild drill: Jenkins' StatefulSet and PVC
       deleted outright, both credential Secrets confirmed to survive
       untouched (they were never stored there), full recovery via the
       same two idempotent scripts used for the original install, and a
       real end-to-end build (webhook -> CI -> CD -> Slack) proving the
       recovered system actually works, not just that it boots.
     - Also documents a real, unrelated finding surfaced by the drill and
       then root-caused after reproducing live a second time: agent Pods
       weren't being cleaned up immediately despite podRetention: never,
       because both agent templates also set idleMinutes: 5 - a direct
       contradiction, fixed by removing it (jenkins/values.yaml).

10-rbac-helm-secret-pruning-fix.txt (referenced above, not its own bonus
item): cd-deploy-sa lacking delete permission on Secrets for Helm's own
release-history storage, found only after several real end-to-end deploys/
rollbacks had accumulated history past Helm's default limit of 10
revisions (jenkins/rbac/cd-deploy-rbac.yaml, commit d3c3eab).

Getting all of this right took a genuinely long chain of real, live-caught
bugs (each documented in its own commit message, not just summarized
here): a wrong Service-CIDR-vs-VPC-CIDR assumption for the controller's
Kubernetes API access; a missing GitHub egress rule for the controller's
own lightweight Jenkinsfile checkout; an incorrect assumption about what
label actually identifies a dynamically-provisioned agent Pod (leading to
two NetworkPolicy objects that looked scoped correctly but matched no real
Pod at all); a missing port-80 rule first misdiagnosed as an unrelated AWS
Classic-ELB networking limitation before being traced to its real cause; a
podSelector-based port-80 rule that resolved correctly at the Kubernetes
API level but was never actually enforced, because AWS VPC CNI evaluates
egress against the pre-DNAT Service ClusterIP, not the Pod IP a
podSelector resolves to; a Kaniko digest file written to a path that
wasn't actually shared across containers; a missing ECR credential helper
for Cosign; Cosign's default public-Rekor-upload behavior silently
reintroducing a dependency the whole KMS-signing design choice was meant
to avoid; a first-round verification "success" that was actually matching
a stale, not-yet-fixed signature instead of the one being tested; the
Helm-history Secret-pruning permission gap above; the PR trigger's
header-name mismatch (item 7); and the agent-Pod idleMinutes contradiction
surfaced during the recovery drill (item 9). Each is why the corresponding
code comment exists - not decoration, but the actual reason that line is
there.
