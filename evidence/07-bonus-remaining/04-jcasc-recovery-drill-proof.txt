JCasC-first recovery (bonus #3) - a real destroy-and-rebuild drill
=====================================================================

Chosen over EBS snapshot/restore: architecturally consistent with how this
whole project already treats infra as reproducible from code (Terraform,
Helm, JCasC) rather than as state to be backed up. The claim under test:
if Jenkins' entire persistent home (PVC) is destroyed, nothing is actually
lost, because nothing that matters was ever stored only there.

--- Before: state captured ---

  $ kubectl get all,pvc -n jenkins
  pod/jenkins-0                Running   ...
  pod/webhook-relay-...        Running   ...
  persistentvolumeclaim/jenkins  Bound  pvc-08e5f148-...  8Gi  ebs-gp3

  $ curl .../api/json?tree=jobs[name]
  {"jobs":[{"name":"cd-application"},{"name":"ci-application"},{"name":"ci-application-pr"}]}

  $ kubectl get secrets -n jenkins -l jenkins.io/credentials-type
  NAME                 TYPE     DATA   AGE
  git-webhook-secret   Opaque   1      18m
  slack-webhook-url    Opaque   1      18m

--- Destroy ---

  $ kubectl delete statefulset jenkins -n jenkins
  statefulset.apps "jenkins" deleted
  $ kubectl delete pvc jenkins -n jenkins
  persistentvolumeclaim "jenkins" deleted

  $ kubectl get pod,pvc -n jenkins
  (jenkins-0 and the PVC both gone; webhook-relay pod, unrelated,
  untouched)

  $ kubectl get secrets -n jenkins -l jenkins.io/credentials-type
  NAME                 TYPE     DATA   AGE
  git-webhook-secret   Opaque   1      19m
  slack-webhook-url    Opaque   1      19m

  Confirms the premise directly: both credential Secrets are separate
  Kubernetes objects, never stored on the Jenkins PVC, and survived the
  deletion completely untouched.

--- Rebuild, purely from code ---

  $ bash jenkins/scripts/install-jenkins.sh
  ==> [5/8] Installing Jenkins (Helm chart + JCasC from jenkins/values.yaml)...
  Release "jenkins" has been upgraded. Happy Helming!
  REVISION: 2
  [OK] Jenkins controller deployed and Ready
  EXIT_CODE=0

  A brand-new PVC was dynamically provisioned by the ebs-gp3 StorageClass;
  JCasC reasserted the entire controller configuration (plugins, the
  Kubernetes cloud, both agent pod templates, the Shared Library) onto
  that empty volume with zero manual steps.

  $ bash jenkins/jobs/create-jobs.sh
  Creating job: ci-application
  Creating job: cd-application
  Creating job: ci-application-pr

  ("Creating", not "Updating" - proof this really was a fresh, empty
  Jenkins home, not a config no-op against surviving state.)

--- Proof it actually works, not just that it boots ---

  A real, GitHub-webhook-triggered ci-application build (commit e38fe50,
  pushed to main during this drill) ran the full matrix build, Trivy
  scan, SBOM generation, and Cosign KMS signing for all three services,
  triggered cd-application automatically, which deployed, rolled out,
  smoke-tested, and both stages notified Slack - all post-recovery, with
  no manual intervention beyond the two idempotent recovery scripts
  themselves. See 03-notifications-proof.txt items 2-3 for the literal
  console excerpts from these exact builds.

--- A real problem found along the way (worth documenting honestly) ---

  The very first post-recovery build attempt failed, but not because of
  anything the recovery drill was testing - ECR correctly rejected
  re-pushing an already-existing immutable tag, because build history
  reset to #1 after the PVC wipe while the underlying commit (and
  therefore the image tag) hadn't changed. This is the tag-immutability
  policy working exactly as designed, not a recovery bug - resolved by
  committing the PR-trigger fix (e38fe50) and pushing, giving the next
  build a genuinely new commit SHA to tag.

  Separately, a real capacity problem surfaced during that same build:

    Pod [Pending][Unschedulable] 0/3 nodes are available: 3 Insufficient
    cpu, 3 Insufficient memory.

  `podRetention: never` (jenkins/values.yaml's agent pod templates) is
  documented to delete each agent Pod immediately after its build - but
  three just-finished matrix-cell Pods from the same build, plus one
  fully-idle PR-agent Pod left over from 26 minutes earlier, were all
  still Running and consuming enough of the 3-node cluster's capacity
  that the next required Pod (the top-level pipeline's own post{} block,
  which needs a fresh agent to run notifySlack()) couldn't schedule at
  all. Manually deleting the clearly-orphaned PR-agent Pod freed enough
  room for the pending Pod to schedule immediately - a workaround at the
  time, not yet a diagnosis.

  --- Update: root-caused and fixed live, same session ---

  The same starvation reproduced live again on the very next real
  build (ci-application #4, triggered by an unrelated later push), this
  time caught in the act: two ci-agent Pods from the *previous*, already-
  SUCCESS build were still fully Running 12+ minutes after that build had
  already notified Slack and finished - `kubectl get pod ... -o
  jsonpath='{.metadata.deletionTimestamp}'` came back empty, meaning
  Jenkins had never even asked Kubernetes to delete them, not that
  deletion was slow.

  Root cause: both the `ci-agent` and `cd-agent` pod templates
  (jenkins/values.yaml) also set `idleMinutes: 5` - which keeps a
  just-finished Pod alive and idle for up to 5 minutes so a later build
  can reuse it without a cold start. That directly contradicts the
  Kubernetes Cloud's own `podRetention: never` (and this project's own
  README, which documents "agents are deleted immediately after their
  build, not kept around") - idleMinutes overrides immediate cleanup with
  a 5-minute idle-reuse window per Pod. On a 3-node t3.medium cluster
  running the Jenkins controller, the webhook relay, and now three jobs'
  worth of ephemeral agent Pods (ci-application's matrix, cd-application,
  ci-application-pr's own matrix) all competing for the same headroom,
  that 5-minute window was long enough for a new build's Pods to arrive
  and find no room left.

  Fixed by removing `idleMinutes` from both templates (not just
  shortening it): this cluster's real constraint is scheduling headroom,
  not agent cold-start latency, so the reuse optimization wasn't worth
  keeping.

  Applied via `install-jenkins.sh` (the same idempotent `helm upgrade`
  used throughout this project) while no build was in flight. Confirmed
  the change actually reached the running controller without a Pod
  restart - `jenkins-0`'s age was unchanged, so the chart's config-reload
  sidecar picked it up live - by POSTing to /configuration-as-code/export
  and grepping the returned config for `ci-agent`/`cd-agent`: no
  `idleMinutes` field on either template.

  Then re-verified with a real build (ci-application #5), watching Pod
  status every 10s:

    t+10s   ci-application-5-9wrxx-...   ContainerCreating (Checkout stage)
    t+50s   ci-application-5-xwt8g-...   Running (matrix cell starts)
    t+80s   ci-application-5-xwt8g-...   Terminating (30s after it started -
            that cell's build step failed fast: ECR rejected the immutable
            tag re-push, same unchanged-commit situation as the earlier
            recovery-drill build - expected, not the point of this test)
    t+110s  ci-application-5-kv4lj-...   Terminating
    t+120s  ci-application-5-8fbw4-...   Terminating,
            ci-application-5-9wrxx-...   Terminating (Checkout Pod, once
            the post{} block's own notifySlack() finished)
    t+150s  (kubectl get pods -n jenkins: no ci-application-5-* Pods left)

  Every Pod gone within ~2.5 minutes of the build starting, each one
  individually within roughly a minute of its own stage finishing - not
  the 12+ minutes observed before the fix. The one Pod still lingering at
  that point (`cd-application-3-...`, Terminating by t+150s) had been
  created *before* the fix was applied, so it was still finishing out its
  old 5-minute idle window - consistent with the diagnosis, not a
  contradiction of it.
